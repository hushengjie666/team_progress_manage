# 核心业务数据的关系型存储

## 存储契约

自 0.2.11 / schema 14 起，11 类业务实体的固定字段由业务表中的 `core_*` 列提供。任务标题、正文、状态、阶段、进度、工时、归属、负责人及时间等不再只依赖 JSON。`team-server/relational-schema.json` 定义字段、嵌套对象及集合，读写模块使用同一份定义；迁移 SQL 固化发布时的数据库结构。

项目角色、任务标签和协作者、每周重复日期、子任务、估算历史、每日计划清单、徽章、模板标签和模板子任务放在 11 张明细表。明细主键是工作区、父记录和位置，保留原集合的顺序及重复值。父记录外键在删除及迁移工作区时级联处理。存在标记区分缺省集合和空集合。

现有 `workspace_id` / `id` / `account_id` 是记录身份及访问控制的依据；`project_id` / `task_id` / `status` 等原索引列仍用于查询，由统一写入路径同步派生。新增列保存业务字段。业务对象中的同名身份字段用于保持接口形状，不能替代记录封装中的权限检查。

`payload` 保留完整接口快照和未知扩展字段。读接口以核心列覆盖快照中的已定义字段，再按位置装配明细；空或陈旧快照不会覆盖核心值。嵌套对象及明细快照中的扩展键继续保留。扩展字段仍依赖 JSON，正式新增核心字段时必须同步修改定义、添加迁移和覆盖测试，不能只往 JSON 中写入。

固定文本列使用 LONGTEXT，数值使用 DOUBLE 对齐客户端 JavaScript 数值，布尔值使用 BOOLEAN。缺失字段保持 NULL，不凭空补历史值。新写入严格检查 JSON 类型，数字字符串、错误对象或集合类型导致整个事务回滚。历史数据缺失不属于本次重构的恢复范围。

## 写入和读取

业务创建、更新和工作区移动都经过统一存储入口。接口快照、核心列、明细和变更记录在同一事务中写入，出错全部回滚。核心读取已接入任务、审阅、工作会话、访问控制和项目邀请等直接 SQL 查询。

读取按实体和明细种类批量查询，每批最多 200 个父记录，避免为每个任务单独读取明细。锁定业务记录的修改路径同时锁定其明细。HTTP 行封装和 JSON 业务对象保持原有形状，API protocol 仍为 2；版本合同要求 0.2.11 客户端与 schema 14 后端一起更新。

## 迁移与回退

`00014_v0_2_11_relational_business.sql` 是唯一新增迁移。Up 在任何表结构变化前检查标量、对象和明细类型，再新增核心列及明细表并填入现存 JSON。MySQL 的 INTEGER、UNSIGNED INTEGER、DOUBLE 和 DECIMAL 均作为数字接受。

已有业务数据的数据库必须先通过近期备份门禁；仅空业务库可跳过这次迁移的备份要求。备份门禁匹配数据库名、schema、时间、文件大小和 SHA-256。备份导出强制显式列名和单行 INSERT，随后核对实际数据库表及列定义、INSERT 列清单和每行值数量。此检查能拒绝少导列的文件，但不能代替隔离库的实际恢复演练。

Up 包含 MySQL 非事务性 DDL。上线前必须从备份恢复独立候选库，逐条比较全部业务 JSON，测试升级、Down 和再次升级。生产切换时停止业务服务，制作新的验证备份，再迁移、启动匹配版本并核对数据和健康状态。若发生部分 DDL 失败，应恢复验证过的升级前备份，不能仅切回旧可执行文件。

Down 从核心列及有序明细重建完整快照，然后移除新增结构，支持回到 schema 13。成功升级后需要回退时，先停止服务、备份当前库，用 0.2.11 的数据库命令执行 Down，再切换旧程序。继续沿用永久 schema 1 基线，不支持回退到基线以下。

## 验证

回归测试覆盖 11 类实体、Unicode 和转义文本、布尔值、非整数数值、空集合、重复及排序、嵌套扩展字段、陈旧快照、无效写入事务回滚，以及可编辑字段的存储定义覆盖。真实 MySQL 测试遍历 schema 1 至 13 的升级、回退及再升级；现有数据库完整性、校验和、数据库版本超前拒绝及备份门禁测试继续运行。

本次正式库备份在独立 MySQL 中恢复后，807 条业务记录逐条语义比较通过：16 个项目、24 个项目成员、111 个任务、61 个每日计划、155 条专注记录、144 条工作记录、290 条执行信号和 6 条奖励状态。升级、回退重建快照和再次升级均保持这些记录一致。备份原件及校验记录保存在受保护的运维目录，不进入 Git 或发布包。
